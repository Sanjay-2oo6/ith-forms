# Razorpay Native Payment Integration

This change upgrades the existing Payment question type from external URL + screenshot workflow to native Razorpay checkout integration. The implementation adds a `payment_transactions` table, two SECURITY DEFINER RPCs for order creation and transaction recording, payment configuration fields in the form builder, and updates the public form renderer, validation, submission pipeline, and admin response display to handle Razorpay payments while maintaining backward compatibility with legacy screenshot-based payments.

**Watch for:** **confirmed** — The payment checkout flow is completely broken. The native mode renderer shows payment details but provides no way for users to actually pay. The plan expected a "Pay Now" button calling `handlePayment()`, but the implementation just displays a message telling users to "sign in to complete payment" with no actionable button. **confirmed** — The created `RazorpayPaymentButton.tsx` component is never imported or used anywhere. **confirmed** — `window.__pendingPayments` is never populated, so payment transactions will never be recorded even if users somehow completed payment. **likely** — No server-side signature verification means the app trusts client-provided payment data without cryptographic proof from Razorpay.

**Verdict**: NEEDS_CHANGES

## High-level view

The database foundation is solid: migration 063 adds a `payment_transactions` table with proper RLS policies, indexes, and two RPCs (`create_razorpay_order`, `record_payment_transaction`) that follow the app's SECURITY DEFINER pattern. The form builder already has payment configuration UI (amount, currency, description) from prior work. The Razorpay SDK script loads correctly via useEffect. Validation logic distinguishes native mode (payment_id string starting with `pay_`) from legacy mode (File array). The submission handler has transaction recording code that reads from `window.__pendingPayments` and calls the RPC after submission creation. Admin response display queries `payment_transactions` and shows status, amount, payment ID, order ID, and verification badge. Export utils detect payment IDs starting with `pay_` and format them appropriately.

However, the public form payment renderer is incomplete. In native mode, it displays payment amount and description but shows only a placeholder message ("Please sign in to complete payment") instead of a clickable "Pay Now" button. The plan called for a button triggering `handlePayment()`, but that function was never implemented. A standalone `RazorpayPaymentButton` component exists but is never imported. The entire checkout flow is non-functional.

## Payment checkout flow gap

The native Razorpay mode renderer in `src/routes/forms/$slug.tsx` (lines 1465-1502) displays payment amount, currency, and description correctly. It checks if payment is complete by testing `paymentId.startsWith("pay_")`. When isPaid is false, the plan expected a button:

```typescript
<button onClick={() => handlePayment(q)} ...>Pay Now</button>
```

The actual implementation shows:

```typescript
<div className="text-sm text-muted-foreground">
  <p className="mb-2">Please sign in to complete payment</p>
  <div className="p-3 bg-secondary/30 rounded-lg border border-border/40">
    <p className="text-xs">Payment processing requires authentication. Click Submit to sign in and complete your payment.</p>
  </div>
</div>
```

This is a placeholder message with no actionable UI. Users authenticated or not have no way to trigger payment. The form cannot collect payments in native mode.

The `RazorpayPaymentButton` component in `src/components/RazorpayPaymentButton.tsx` contains the complete payment flow logic: validates env vars, calls `create_razorpay_order` RPC, opens Razorpay modal with correct options, handles success callback by calling `onSuccess(payment_id, response)`. But this component is never imported in $slug.tsx. Grep search for "RazorpayPaymentButton" in the form route returns no matches.

## Payment transaction recording pipeline

The submission handler (lines 602-628 in $slug.tsx) correctly implements the plan's transaction recording step. After `submit_response` RPC returns a submission_id, it loops through payment questions in native mode, reads `window.__pendingPayments[q.id]`, and calls `record_payment_transaction` RPC with the submission_id and payment details. If recording fails, it logs an error but doesn't fail the submission (correct behavior since payment already captured).

However, this entire pipeline is dead code. `window.__pendingPayments` is never written to. The `RazorpayPaymentButton` component's success handler includes this line:

```typescript
(window as any).__pendingPayments[question.id] = {
  order_id: response.razorpay_order_id,
  payment_id: response.razorpay_payment_id,
  signature: response.razorpay_signature,
  amount: amount,
  currency: currency,
};
```

But since the component is never used, this never executes. Even if a user somehow obtained a valid Razorpay payment_id and manually set `answers[question.id] = "pay_..."`, the transaction wouldn't be recorded because the pendingPayments object is empty.

## Server-side order creation gap

The `create_razorpay_order` RPC (lines 76-108 in migration 063) generates an order_id locally:

```sql
v_order_id := 'order_' || encode(gen_random_bytes(12), 'hex');
```

Then returns it in a jsonb response. This satisfies the return type contract the client expects, but it's not a real Razorpay order. Razorpay's checkout SDK requires an order_id created via their Orders API (`POST https://api.razorpay.com/v1/orders`), which requires the Razorpay secret key for authentication.

Real integration would need:
1. Store `RAZORPAY_KEY_SECRET` in Supabase secrets (never client-exposed)
2. In the RPC, make HTTP request to Razorpay Orders API with Basic Auth (key_id:key_secret)
3. Parse the response and extract the real order_id
4. Return that order_id to the client

Without this, when users click "Pay Now" and Razorpay checkout opens with the fake order_id, Razorpay will reject it as invalid.

The plan acknowledges this gap in the "Gotchas" section: "Signature validation is implicit in Razorpay's order creation flow (not implemented in our RPC, assumed Razorpay handles it)". This assumption is incorrect. The RPC must call Razorpay's API.

## Payment signature verification

The `record_payment_transaction` RPC accepts `p_razorpay_signature` parameter and stores it, but never verifies it. Razorpay's payment verification requires computing HMAC-SHA256 of `order_id|payment_id` using the secret key, then comparing it to the provided signature. Without this, a malicious user could submit fake payment_id values and the app would accept them as verified=true.

The RPC unconditionally sets `verified = true` on line 182 of migration 063. This is a critical security gap for a payment system.

## Validation logic correctness

The `requiredMissing` function (lines 376-384 in $slug.tsx) correctly distinguishes native mode from legacy mode:

```typescript
if (q.type === "payment") {
  const isNativeMode = (q.config?.razorpayAmount ?? 0) >= 100;
  if (isNativeMode) {
    return !val || (typeof val === "string" && !val.trim());
  }
  return !val || (Array.isArray(val) && val.length === 0);
}
```

Native mode expects a non-empty string (payment_id), legacy mode expects a File array. The 100 paise threshold prevents misconfiguration (Razorpay minimum is 100 paise = ₹1). This matches the same threshold check used in the renderer, transaction recording, and admin display.

## Answer payload filtering

The submission handler (lines 535-548 in $slug.tsx) correctly includes payment questions in native mode and excludes them in legacy mode:

```typescript
if (q.type === "payment") {
  const isNativeMode = (q.config?.razorpayAmount ?? 0) >= 100;
  return isNativeMode;
}
```

In native mode, the payment_id string is included in the answer payload sent to `submit_response` RPC. In legacy mode, payment questions are excluded (screenshots handled via file upload pipeline). This prevents submitting File objects as answer values and ensures payment_id is stored in the answers table.

## Admin response display

`SubmissionDetailModal.tsx` (lines 150-178, 367-441) properly queries `payment_transactions` table on mount for all native-mode payment questions, maps results by question_id, and displays transaction details. The UI shows:
- Payment status with color coding (green for captured, red for failed, yellow for pending)
- Amount formatted by currency (₹ symbol for INR, currency code otherwise)
- Payment ID and Order ID in monospace font with truncation
- Verification badge when tx.verified is true

The query uses `.in("question_id", paymentQuestions.map(q => q.id))` to batch-fetch all transactions for the submission in one query. RLS policy `user_read_own_payments` allows users to read their own payments, `admin_read_payments` allows admins to read all.

Legacy mode falls back to showing payment URL link and screenshot upload status. The conditional rendering correctly detects mode and renders appropriate UI for both cases and for missing configuration.

## Export formatting

`export-utils.ts` (lines 47-52) detects native mode by checking if the answer value starts with `pay_` (Razorpay payment ID format):

```typescript
if (rawValue && rawValue.startsWith("pay_")) {
  return `Payment completed (ID: ${rawValue})`;
}
return rawValue ? "Payment completed - screenshot uploaded" : "No proof uploaded";
```

This provides meaningful export data without exposing file paths. However, the plan's Step 9 calls for enhanced export with separate columns for status, amount, payment ID, and verified flag by joining with `payment_transactions` table. The current implementation only exports the payment_id string. Admins exporting responses won't see payment amounts or statuses.

The plan notes "Better approach: Update the export query to JOIN with `payment_transactions` table and include amount, status, payment_id as separate columns" but this wasn't implemented. The plan defers this to finding where the export logic lives and modifying it there.

## Razorpay SDK loading

The useEffect at lines 174-191 in $slug.tsx correctly loads the Razorpay checkout script dynamically:

```typescript
useEffect(() => {
  if (document.querySelector('script[src*="checkout.razorpay.com"]')) {
    return;
  }
  const script = document.createElement('script');
  script.src = 'https://checkout.razorpay.com/v1/checkout.js';
  script.async = true;
  script.onload = () => console.log('[Razorpay] Checkout script loaded');
  script.onerror = () => console.error('[Razorpay] Failed to load checkout script');
  document.head.appendChild(script);
}, []);
```

The guard prevents duplicate script tags. The async attribute ensures non-blocking load. The empty dependency array means it runs once on mount. This is the correct pattern for third-party SDK loading in React. `window.Razorpay` will be available when the script finishes loading.

## Database migration safety

Migration 063 follows the app's migration patterns. The `payment_transactions` table has proper foreign keys with ON DELETE CASCADE to clean up orphaned records when submissions/forms/questions are deleted. The `razorpay_order_id` UNIQUE constraint prevents duplicate transaction recording (idempotent). The status CHECK constraint limits values to the documented enum. RLS policies follow the app's `is_admin()` pattern. Indexes on submission_id, order_id, and payment_id support common query patterns.

Both RPCs are SECURITY DEFINER with `SET search_path = public` to prevent search_path attacks. They verify `auth.uid() IS NOT NULL` before proceeding. `GRANT EXECUTE ... TO authenticated` restricts access to logged-in users. These follow the same security model as the existing `submit_response` RPC.

The migration is idempotent (CREATE TABLE IF NOT EXISTS, CREATE OR REPLACE FUNCTION) so it can be re-run safely.

## Backward compatibility handling

The implementation correctly preserves legacy payment questions. The renderer checks `isNativeMode = (razorpayAmount ?? 0) >= 100` and falls back to legacy UI if false. Legacy mode shows the external payment URL link with target="_blank" rel="noopener noreferrer" security attributes, followed by FileUploader for screenshot upload restricted to .jpg/.jpeg/.png with 10MB limit.

Validation checks legacy mode File array length. Answer payload filtering excludes legacy payment questions so screenshots go through file upload pipeline. Admin display shows legacy URL and screenshot status. Export shows "screenshot uploaded" for legacy mode.

Old published forms with paymentUrl configured continue working unchanged. New forms configured with razorpayAmount use native mode. Forms can't be in both modes simultaneously since the builder UI replaced paymentUrl input with amount/currency/description inputs.

However, there's no migration path documented. If an admin wants to convert an existing legacy payment question to native Razorpay, they'd need to manually reconfigure it in the builder. The plan doesn't address this scenario.

## Environment configuration

`.env.example` was updated correctly (lines 11-17):

```
# Razorpay Configuration (for native payment integration)
# Get your key_id from Razorpay Dashboard > Settings > API Keys
# This is the PUBLIC key (key_id), NOT the secret key
# Starts with rzp_test_ (test mode) or rzp_live_ (production)
# Payment verification happens server-side via Razorpay signature validation
VITE_RAZORPAY_KEY_ID=rzp_test_your_key_id_here
```

The comments correctly distinguish public key_id from secret key and mention test/live modes. However, the comment "Payment verification happens server-side" is misleading since the implementation doesn't perform server-side verification.

The `RazorpayPaymentButton` component checks for the env var:

```typescript
const razorpayKeyId = import.meta.env.VITE_RAZORPAY_KEY_ID;
if (!razorpayKeyId) {
  toast.error("Payment system not configured. Please contact the administrator.");
  return;
}
```

But since the component isn't used, this validation never runs. If someone deployed the app without setting the env var, they'd discover the problem only after reading browser console errors (assuming the payment button existed).
