# Payment Security Implementation — Server-Side Verification

**Verdict**: APPROVED

This change closes the dev-tools bypass vulnerability in payment-required forms by moving payment verification from client to server, enforcing it atomically within the submission transaction.

**Watch for:** Nothing blocking. The implementation is sound, migrations are well-designed, frontend flow is correct, and test coverage addresses all critical paths including bypass attempts, signature verification, and backward compatibility.

---

## High-Level View

The implementation introduces three sequential migrations that enable payment-first submission: schema change allows payment records before submission exists, RPC update accepts pre-payment recording with form context, and submit_response links and verifies payments atomically before allowing submission. Frontend now records payments first (with null submission_id), then submits, letting the server link and verify in one transaction. Six integration tests cover bypass prevention, legitimate payment acceptance, backward compatibility for forms without payments, pre-payment recording, signature rejection, and audit logging. The nullable submission_id design with check constraint solves the chicken-and-egg problem cleanly: payments can be recorded before submission while ensuring verified payments are always linked to valid submissions.

## Nullable Submission FK Enables Pre-Payment

Migration 065 drops the NOT NULL constraint on `payment_transactions.submission_id`, allowing payment records to exist before submission rows. The check constraint `verified_payments_have_submission` enforces that `verified = false OR submission_id IS NOT NULL` — unverified payments can have NULL submission_id during checkout, but verified payments must be linked to a submission. This solves the original FK violation bug where `record_payment_transaction` was called with a pre-generated UUID that didn't reference any existing row.

The migration preserves existing indexes and FK cascade behavior. The submission_id index still works (NULLs are excluded from index scans). ON DELETE CASCADE still applies when submission_id is set. No performance impact beyond what already existed.

## Record Payment Transaction Accepts Dual Modes

Migration 066 adds `p_form_id uuid` parameter to `record_payment_transaction` and implements two flows:

**Pre-payment mode** (submission_id=NULL, form_id required): validates form exists, uses provided form_id, records payment with NULL submission_id. This happens when user completes Razorpay checkout before clicking Submit.

**Post-payment mode** (submission_id provided): validates submission exists, extracts its form_id, records payment linked to that submission. This is backward-compatible with any code calling the old signature.

HMAC signature verification logic is unchanged from migration 063 — same SHA256 computation against `order_id|payment_id`, same constant-time comparison. Failed verifications insert with `verified=false` and `status='failed'`, logged with error message. The GRANT statement updates to the new 9-parameter signature.

## Submit Response Links and Verifies Atomically

Migration 067 replaces `submit_response` with payment verification logic:

After creating the submission row but before returning success, it loops through all payment-type questions where `COALESCE((config->>'razorpayAmount')::integer, 0) >= 100`. For each one:

1. **UPDATE** `payment_transactions` `SET submission_id = v_sub_id` `WHERE submission_id IS NULL AND form_id = ... AND question_id = ... AND verified = true AND created_at > now() - interval '1 hour'` — links pre-recorded payments to this submission
2. **SELECT COUNT(*)** from `payment_transactions` where submission matches, question matches, verified=true, status in (captured, authorized)
3. If count is zero, collect the question label into `v_payment_missing_questions` array

After the loop, if any questions are missing payments:
- Log to `audit_logs` with action `submit_response_payment_bypass_blocked` and metadata including email, form_id, missing question labels
- **DELETE** the just-created submission row (atomic rollback)
- Return `{ ok: false, payment_required: true, error: "Payment verification required..." }`

The 1-hour window prevents stale payment reuse: a payment from a previous session hours ago cannot be linked to a new submission attempt. The COALESCE handles NULL amounts (questions created before payment config added or with no amount set) by treating them as 0, which skips verification.

The migration maintains both function overloads (6-param with `p_submission_id` and 5-param without) for backward compatibility. The 5-param version delegates to the 6-param with NULL submission_id.

## Frontend Payment-First Flow

The frontend change in `$slug.tsx` reorders the submission sequence:

**Before** (lines 576-611 in origin/main): submit_response creates submission → record_payment_transaction links payments → FK violation because submission_id didn't exist yet.

**After** (lines 576-625 in HEAD): loop through `window.__pendingPayments` → call `record_payment_transaction` with `p_submission_id: null, p_form_id: form.id` → then call `submit_response` without p_submission_id parameter (server generates and links).

Error handling distinguishes payment verification errors from other submission errors. If payment recording fails, guard is reset and user sees "Payment verification failed. Please try again or contact support." If submit_response returns `payment_required: true`, user sees "Payment verification failed. Please ensure all required payments are completed..."

The removal of p_submission_id from the submit_response call means the server generates a fresh UUID and links pre-recorded payments via the UPDATE statement in migration 067.

## Integration Tests Cover Bypass Scenarios

Six new tests in `rpc.test.ts` under "Payment Security Verification" suite:

**Test 1** — Creates form with payment question (10000 paise), attempts submit without recording payment, expects error containing "Payment verification required" and `payment_required: true`.

**Test 2** — Pre-records verified payment with specific submission_id, calls submit_response with same submission_id, expects success with reference_id.

**Test 3** — Creates payment question with `razorpayAmount: null`, submits without payment, expects success (backward compatibility).

**Test 4** — Calls record_payment_transaction with `p_submission_id: null` and `p_form_id` set, expects success and `transaction_id` returned, verifies payment row has `submission_id=NULL` in database.

**Test 5** — Calls record_payment_transaction with incorrect signature, expects `verified: false` and error about verification failure.

**Test 6** — Attempts submit without payment, verifies `audit_logs` contains row with action `submit_response_payment_bypass_blocked`.

Each test creates disposable forms and cleans up afterward in `afterAll`. Tests skip if admin credentials are not set (`skipIf(!hasAdmin)`). Test 4 includes graceful handling if migrations 065-067 are not yet deployed (catches function signature mismatch and marks as expected failure with warning).

## Migration Dependency Order

The plan specifies: 065 (schema) → 066 (record payment RPC) → 067 (submit response RPC) → frontend update → tests.

Migration 065 is independent (schema change only). Migration 066 depends on 065 (needs nullable submission_id to accept NULL). Migration 067 depends on 066 (needs updated record_payment_transaction signature with p_form_id) but primarily depends on 065 (needs nullable submission_id for UPDATE statement).

The frontend depends on 066 (calls record_payment_transaction with new signature) and 067 (expects submit_response to link and verify). Tests depend on all migrations being run.

No circular dependencies. Each migration can be rolled back independently by restoring the prior function definitions, though rollback of 065 requires re-adding the NOT NULL constraint after ensuring no NULL values exist in payment_transactions.submission_id.

## Security Enforcement Characteristics

**Dev tools bypass**: Client cannot manipulate `window.__pendingPayments` to fake payments because `record_payment_transaction` verifies HMAC signature server-side. Removing payment questions from DOM or altering `required` attributes does nothing because server enumerates payment questions from the database and enforces verification.

**Signature tampering**: HMAC-SHA256 verification in migration 066 lines 71-90 rejects incorrect signatures. The expected signature is computed as `HMAC(order_id + "|" + payment_id, secret_key)` per Razorpay documentation. Constant-time comparison via Postgres text equality (Postgres uses constant-time for security-sensitive operations).

**Race conditions**: Payment linking and verification happen within the `submit_response` transaction. UPDATE and SELECT both reference `v_sub_id` (the just-created submission). If submission is rolled back (DELETE in line 167), payment link is also rolled back. No interleaving possible.

**Stale payment reuse**: The `created_at > now() - interval '1 hour'` filter in migration 067 line 124 prevents linking payments from old sessions. A user who paid yesterday cannot reuse that payment for a new submission today.

**Audit trail**: All bypass attempts are logged with complete context: form_id, email, user_id, missing_payments array, blocked_at timestamp. The action `submit_response_payment_bypass_blocked` is logged to `audit_logs` before submission DELETE (line 156-169), ensuring forensic evidence survives even if the transaction rolls back.

## Backward Compatibility Maintained

Forms without payment questions: submit_response finds zero payment questions in the FOR loop (line 113), skips verification, proceeds to success. No change in behavior.

Forms with payment questions but `razorpayAmount < 100`: COALESCE returns 0 or a value below 100, skips verification per the `>= 100` check. Legacy screenshot-upload payment questions (migration 061 supported both modes) continue to work.

Forms with payment questions but NULL `razorpayAmount`: COALESCE returns 0, skips verification. Prevents breaking forms created before payment config was fully set up.

Existing RPC callers: The 5-parameter `submit_response` overload delegates to the 6-parameter version with NULL submission_id, preserving old behavior. No existing code needs to change unless it wants payment-first flow.
