# Native Razorpay Payment Integration

Integration adds Razorpay checkout to payment questions, replacing external URL + screenshot upload. Questions configured with `razorpayAmount >= 100` render a payment button that opens Razorpay's hosted checkout; on success the `payment_id` is stored in form answers and a transaction record is written to the new `payment_transactions` table via Supabase RPC. Legacy questions (with `paymentUrl` set) continue to use the screenshot workflow.

**Watch for:** The RPC layer that records payment transactions (`record_payment_transaction`) **does not verify Razorpay signatures server-side**. Migration 063 includes explicit TODO comments stating this, but the client code marks every transaction as `verified: true` without actual HMAC-SHA256 validation. A malicious user can submit a fake `payment_id` and it will be accepted as genuine. Additionally, `create_razorpay_order` generates a local `order_id` instead of calling Razorpay's Orders API, meaning Razorpay's checkout will reject the order. **The integration is a security-critical stub that must not be deployed to production without implementing real signature verification and order creation.**

**Verdict**: NEEDS_CHANGES

---

## High-level view

The Razorpay key is correctly sourced from `VITE_RAZORPAY_KEY_ID` and only used client-side to initialize checkout. The payment flow is structurally sound: order creation RPC → checkout modal → success callback stores `payment_id` in form state → submission handler records transaction → cleanup. Payment questions render three modes: native Razorpay (amount configured), legacy screenshot (URL configured), or error (neither). The validation correctly distinguishes between native mode (payment_id string) and legacy mode (File array). The response detail modal queries `payment_transactions` and displays amount, status, and Razorpay IDs. Export utilities recognize native payment answers by the `pay_` prefix.

The gating security issue is that both RPCs in migration 063 are stubs: `create_razorpay_order` generates a fake order_id locally instead of calling Razorpay's API, and `record_payment_transaction` sets `verified: true` without checking the HMAC-SHA256 signature. The migration file itself documents this with multi-line TODO comments, but the client code assumes the RPCs are production-ready and treats every payment as verified. Razorpay's hosted checkout requires a real order_id from their Orders API; the fake one will cause checkout to fail at runtime. Even if order creation is fixed, the lack of signature verification means an attacker can submit `razorpay_payment_id: "pay_fake123"` and the system will record it as captured and verified.

Type safety is clean: TypeScript declarations for `window.Razorpay` are inline in `RazorpayPaymentButton.tsx`, the payment button component is strongly typed, and the `typecheck` command reported no errors (per the coder's verification log). The Razorpay SDK script is loaded dynamically via `useEffect` in the form component with error handling. The `.env.example` file documents that `VITE_RAZORPAY_KEY_ID` is the public key and that signature verification is not yet implemented.

UX error states are handled: if Razorpay SDK fails to load the button shows a toast; if `VITE_RAZORPAY_KEY_ID` is missing the button refuses to proceed; if amount is misconfigured the renderer shows a red error box. The success state displays a green checkmark "Payment completed" below the amount card. The pending-payments pattern (storing transaction details in `window.__pendingPayments` until submission succeeds) works around the timing constraint that `record_payment_transaction` needs a `submission_id` that doesn't exist until after the form RPC returns.

The mode detection logic is sound. The 100-paise threshold prevents configuration errors where the admin enters rupees instead of paise (e.g., entering `10` meaning ₹10, which is only 10 paise). The legacy path preserves backward compatibility for existing published forms.

1. Validate all answers including payment questions (line 473).
2. Build the answers payload (lines 495-517). Payment questions are included if in native mode (lines 501-508): the filter excludes display-only types and file types *except* payment in native mode, which is a string not a File array.

4. **Record payment transactions** (lines 602-633). 5. Upload files to storage and register via RPC (lines 636-703).

The ordering is correct: submission must exist before recording payment transactions (they need the `submission_id`). Payment recording happens before file uploads, so if a transaction recording fails the user sees the success page but the payment isn't linked. The choice to not fail the submission if recording fails is reasonable (payment was already captured by Razorpay, failing the submission would orphan it), but the log-only error handling means the admin has no visibility into recording failures. The comment on line 626 suggests manual verification via Razorpay dashboard as the fallback.

The RPC parameters match the migration signatures exactly (lines 125-133 of migration 063): `p_submission_id`, `p_question_id`, `p_razorpay_order_id`, `p_razorpay_payment_id`, `p_razorpay_signature`, `p_amount`, `p_currency`, `p_status`. ## Security: missing signature verification (critical)

Migration 063 documents the missing signature verification in a multi-line TODO comment (lines 118-123):

```
-- TODO SECURITY: This RPC accepts razorpay_signature but does NOT verify it.
-- For production, this should:
--   1. Compute HMAC-SHA256 of (razorpay_order_id + '|' + razorpay_payment_id) using RAZORPAY_KEY_SECRET
--   2. Compare computed signature to p_razorpay_signature using constant-time comparison
--   3. Only set verified=true if signatures match
-- Without this, a malicious user can submit fake payment_id values and they'll be accepted as verified.
```

The RPC function `record_payment_transaction` (lines 127-190 of migration 063) unconditionally sets `verified: true` at line 183. It accepts the signature parameter (line 134) and stores it in the table (line 177), but never validates it. The client code (`$slug.tsx` line 619) passes the signature from Razorpay's success callback, assuming the server will verify it.

Razorpay's signature verification works as follows (per Razorpay docs):
1. Concatenate `razorpay_order_id` + `"|"` + `razorpay_payment_id`.
2. Compute HMAC-SHA256 of that string using `RAZORPAY_KEY_SECRET` as the key.
3. Compare the computed hash (hex-encoded) to the `razorpay_signature` sent by Razorpay.
4. Use constant-time comparison to prevent timing attacks.

Without this check, an attacker can:
1. Inspect the Razorpay checkout flow in devtools to see the format of the success response.
2. Submit a form, but instead of paying, call `setAnswers({ questionId: "pay_fake123" })` in devtools.
3. Forge the `window.__pendingPayments` object with fake transaction details.
4. Submit the form. The client will call `record_payment_transaction` with `razorpay_payment_id: "pay_fake123"` and a random signature.
5. The RPC will accept it and mark it as `verified: true`.
6. The admin sees a verified captured payment that was never paid.

The mitigation is that the RPC requires an authenticated session (`auth.uid()` check at lines 138-146), so anon users can't exploit this. But any user with a Google account can submit a form, so the attack surface is anyone with access to the form. The impact is financial fraud: free submissions to forms that require payment.

The fix is to implement the TODO: retrieve `RAZORPAY_KEY_SECRET` from Supabase vault (requires setting it via `supabase secrets set`), compute the HMAC-SHA256 using pgcrypto extension's `hmac` function, compare using `=` (Postgres does constant-time comparison for bytea types), and only set `verified: true` if they match. If the signature is invalid, set `verified: false` and `status: 'failed'`, or reject the transaction entirely and return `{ ok: false, error: "Invalid signature" }`.

Until signature verification is implemented, the integration cannot be deployed to production. The coder correctly documented the limitation in `.env.example` (lines 26-33) and the migration file, but the client code treats the RPCs as production-ready, which creates a false sense of security.

## Security: fake order_id causes checkout failure (critical)

The `create_razorpay_order` RPC (lines 79-120 of migration 063) generates a local order_id using `gen_random_bytes(12)` (line 115). The format matches Razorpay's pattern (`order_<hex>`), but Razorpay's checkout SDK will reject it because the order doesn't exist in Razorpay's system.

When `RazorpayPaymentButton` opens checkout with this order_id (line 111 of `RazorpayPaymentButton.tsx`), Razorpay's backend will return an error like "Order not found" or "Invalid order_id". The checkout modal will show an error to the user, and the payment will fail before reaching the success callback. The user cannot complete payment at all.

The migration documents this in a TODO comment (lines 70-76):

```
-- TODO SECURITY: This RPC generates a local order_id but does NOT call Razorpay's Orders API.
-- For production, this should:
--   1. Store RAZORPAY_KEY_SECRET in Supabase vault
--   2. Install the http extension (requires superuser, Supabase Projects have it)
--   3. Make POST request to https://api.razorpay.com/v1/orders with Basic Auth (key_id:key_secret)
--   4. Return the real order_id from Razorpay's response
-- Without this, Razorpay checkout will reject the fake order_id.
```

The fix is to call Razorpay's Orders API from the RPC. Supabase projects have the `http` extension installed by default. The RPC should:
1. Retrieve `RAZORPAY_KEY_SECRET` from vault.
2. Construct the request body: `{ amount: p_amount, currency: p_currency, receipt: <unique_receipt_id> }` (JSON).
3. Encode `key_id:key_secret` as base64 for Basic Auth.
4. Call `http_post('https://api.razorpay.com/v1/orders', json_body, headers: { 'Authorization': 'Basic <base64>', 'Content-Type': 'application/json' })`.
5. Parse the response JSON and extract `id` (the real order_id).
6. Insert a row in `payment_transactions` with status='created' (the order exists but payment hasn't been captured yet).
7. Return `{ ok: true, order_id: <real_id>, amount, currency }`.

The benefit of creating the order server-side (beyond making checkout work) is that you can set a `receipt` field (a unique identifier you control) and query Razorpay's Payments API later by receipt to reconcile transactions. You can also set `notes` metadata and payment capture settings.

Until real order creation is implemented, the payment button will fail at runtime. The integration is broken in its current state. The coder likely didn't test the checkout flow with a real Razorpay account, or they would have hit this error immediately.
